# Phase 4 acceptance and test mapping

Updated November 1, 2026. This is a source-level inventory for the Phase 4 delivery candidate, **not a deployed acceptance report**. Requirement IDs and declared statuses come from [the recovered Phase 2 v1.0.0 contract](../contracts/phase2-v1.0.0.openapi.json); the AC mapping follows [the reconciliation record](phase2-contract-reconciliation.md). The instructor's system/tester control protocol is a separate interface.

## Runners, counts, and evidence boundaries

| Runner / artifact | What it exercises | How to interpret it |
| --- | --- | --- |
| [`incident_suite.py`](../incident_suite.py), configured by [`delivery_app.py`](../delivery_app.py) | Black-box HTTP incident operations through tester setup/run/report controls | **46 result IDs: 41 executable checks and five explicit gap skips.** A self-run can produce 41 passes and five skips; report actual outcomes for each run. |
| [`contract_audit.py`](../contract_audit.py) | Real application routes in a disposable local store, with a nine-operation status table | `python -m contract_audit --format markdown` or `--format json`. It never targets a deployed service. Its **44 observed checks** are a different inventory from the 46-result HTTP suite. |
| Root `test_*.py` files | Unit, API, persistence, concurrency, control-protocol, transport, and composition regressions | `python -m pytest -q`. Pytest parametrizations contribute separately to its collected case count. Do not add these counts to a black-box run or label them deployed acceptance counts. |
| `SuiteReport.coverage` and `SystemReport.coverage` | Reported code/component/system measurements and their basis | Unknown counts stay `null`. Passing case counts are not line coverage, component coverage, or agreed AC coverage. |

The HTTP suite uses `phase2_schema.validate_response` against the preserved contract: expected status, JSON type/schema, required properties, date-time formats, and an empty body for `204`. Case-specific assertions then check storage, state, relationships, and draft constraints. For a declared status with no response-body schema, such as create `415`, the baseline check proves the status only; local structured-error tests provide separate evidence.

Every mutation is restricted to the exact server-configured isolated own system base and requires a successful `reset.isolated` result first. Failure of reset blocks subsequent writes; prerequisite failures produce skips rather than invented passes. Approval to contact a target is not approval to reset its data. On the currently configured Team 102 base, only `health.ok`, `list.read-only`, `list.invalid-state`, and `get.unknown` can execute without incident setup; mutation cases and their dependent reads skip. These probes can expose an interface mismatch but cannot establish full peer conformance.

## Request-alignment regressions

These six corrected observations are included in the HTTP inventory and are independently checked at model, dependency, and real-route boundaries.

| Contract constraint | HTTP case | Local test function(s) / oracle |
| --- | --- | --- |
| Optional create `source` may be omitted but cannot be explicit null | `regression.create-null-source` | `test_request_models.test_optional_field_omission_and_explicit_null_have_different_meanings`; `test_request_alignment.test_invalid_optional_value_or_timezone_does_not_create_an_incident`. Compare accepted omission against rejected null; invalid request creates no row. |
| Optional review `rationale` may be omitted but cannot be explicit null | `regression.review-null-rationale` | Same optional-field model test; `test_request_alignment.test_explicit_null_review_does_not_write_a_decision_or_history`. Assert unchanged incident and no appended review. |

| Related-body extensions are permitted and ignored | `regression.related-extension` | `test_request_models.test_related_request_accepts_extensions_without_persisting_or_redefining_them`; `test_request_alignment.test_related_extension_fields_are_accepted_without_becoming_incident_data`. | Primary review lookup precedes validation of decoded fields | `regression.review-lookup-before-validation` | `test_request_preparation.test_unknown_incident_precedes_decoded_body_field_validation`; `test_request_alignment.test_incident_lookup_precedes_decoded_body_field_validation`. Lookup-before-field-validation is not a claim that malformed JSON receives `404`.
